Le menu complet mesure environ 770 px de large. Avec le logo et les marges, il lui faut plus de 1000 px. En dessous, il écrasait le logo et coupait le bouton « Réserver ». D'où trois paliers plutôt qu'un seul.

En ajoutant un lien au menu, lui donner class="only-desktop only-large" (palier secondaire) et vérifier qu'il ne déborde pas : redimensionner à 1079 et 730 px, puis contrôler que document.documentElement.scrollWidth - innerWidth vaut bien 0 et que le logo garde sa largeur. 5. Déploiement

Site 100 % statique. Render redéploie automatiquement à chaque push GitHub.

1. git push sur ahmeddavidfp-spec/tremorsi-site (branche main)
2. Render détecte le commit et publie (static site, publish dir ., pas de build)
3. Cloudflare sert le domaine et redirige www vers l'apex

Développement local

cd "Tre Mor Si"
python3 -m http.server 8765     # http://localhost:8765

Publier une modification

git add -A && git commit -m "description" && git push
# Render redéploie en ~1 minute

Attention : garder les CNAME du site en DNS only. Passer en proxy orange empêche Render de vérifier le domaine et de renouveler son certificat.

Supprimer une page : Render garde les fichiers effacés

La publication statique de Render est incrémentale : elle ajoute et écrase, mais ne retire jamais. Un fichier supprimé du dépôt continue d'être servi en 200 après le déploiement, alors que tous les liens vers lui ont bien disparu.

  • Retirer la page du dépôt, des trois navigations, du sitemap.xml et de llms.txt
  • Puis dans le dashboard Render : service tremorsi → Manual Deploy → Clear build cache & deploy
  • Vérifier : curl -o /dev/null -w "%{http_code}" https://tremorsi.com/la-page.html doit rendre 404
Le render.yaml du dépôt n'est pas lu. Le service a été créé à la main dans le dashboard, pas depuis un Blueprint. Preuve : l'en-tête X-Frame-Options qu'il déclare n'est jamais servi. Toute règle ajoutée dans ce fichier (redirections, en-têtes) reste donc sans effet - il faut passer par le dashboard, ou rattacher le service au Blueprint.
Cache CDN : les pages sont servies avec s-maxage=300. Après un déploiement, une vérification en ligne peut renvoyer l'ancienne version pendant quelques minutes. Ajouter un paramètre anti-cache pour tester la vraie version : https://tremorsi.com/page.html?cb=1.
Node (nécessaire pour wrangler) est installé en portable : export PATH="$HOME/tools/node/bin:$PATH" avant toute commande npx.

6. Email & formulaires

Réception - Cloudflare Email Routing actif

Gratuit, illimité en alias. Redirige vers une boîte existante.

  • contact@tremorsi.com → david@bems.be
  • MX, SPF et DKIM posés et verrouillés par Cloudflare
  • Console : zone tremorsi.com → E-mail → Email Routing

Envoi - FormSubmit

Service gratuit sans compte ni backend, appelé en AJAX.

  • Formulaires devis et contact → contact@tremorsi.com
  • Confirmation « ✓ Message envoyé ! » sans quitter la page
  • Repli automatique sur mailto: si l'envoi échoue
Le tout premier envoi déclenche un email d'activation FormSubmit à cliquer (une seule fois, définitif).

Ajouter une adresse de destination

Cloudflare → Email Routing → Adresses de destination → ajouter → la personne clique le lien de vérification reçu → créer/modifier la règle de routage.

7. Agenda, Instagram & bot Telegram

Le client gère sa semaine depuis Telegram, sans toucher au code. Le site se met à jour en quelques secondes.

Tressy écrit au bot @TreMorSiBot (boutons, aucune commande à retenir)
Worker Cloudflare agenda.tremorsi.com reçoit le webhook signé et écrit dans KV
tremorsi.com lit GET /agenda → bandeau du jour + semaine de la page contact

Parcours utilisateur

  • Elle écrit au bot → menu : 📅 Voir la semaine / ✏️ Modifier un jour
  • Choisit le jour → tape le lieu → tape les horaires → « ✓ C'est en ligne sur tremorsi.com ! »
  • Bouton 😴 Repos ce jour-là pour marquer un riposo
  • Bouton 🔑 Code du jour : le code à donner aux clients pour tamponner leur Passaporto
  • Un client montre un code de 6 caractères ? Elle le renvoie au bot, qui répond valide / incomplet / déjà utilisé
ÉlémentValeur
Codeworker/src/index.js
EndpointsGET /agenda · GET /instagram · GET /votes · POST /vote · GET /passaporto · POST /timbro · POST /contatto · POST /telegram
StockageCloudflare KV, namespace AGENDA : week, votes, pass:<id>, riscatto:<id>, c:<heure>:<ip>
CORSLe préflight OPTIONS doit être traité avant le routage, sinon tout POST en JSON est rejeté (voir l'encadré)
SecretsBOT_TOKEN, WEBHOOK_SECRET, ALLOWED_IDS
SécuritéWebhook validé par secret_token + liste blanche d'identifiants Telegram

Piège CORS déjà rencontré. Un fetch qui envoie Content-Type: application/json déclenche d'abord une requête OPTIONS (préflight). Si le test request.method === 'OPTIONS' est placé après les tests de route, cette requête tombe dans le handler du chemin, qui répond 405 - et le navigateur bloque le POST avec un message de CORS, pas d'erreur serveur. C'est ce qui a fait échouer silencieusement tous les votes de la page « Dove andiamo ? » en production. Le test doit être la première ligne du fetch(). Vérification : 
curl -o /dev/null -w "%{http_code}\n" -X OPTIONS https://agenda.tremorsi.com/timbro \
  -H 'Origin: https://tremorsi.com' -H 'Access-Control-Request-Method: POST' \
  -H 'Access-Control-Request-Headers: content-type'   # doit rendre 200

Déployer une modification du Worker

export PATH="$HOME/tools/node/bin:$PATH"
cd worker && npx wrangler deploy
Endpoint FormSubmit : les formulaires appellent le jeton 858b83dc2426a3819b7508c8cd8a0a98 et non contact@tremorsi.com en clair, pour ne pas exposer l'adresse dans le code source. Le premier envoi depuis un domaine donné déclenche un email d'activation à cliquer une fois - à refaire si le domaine change.

Notification Telegram des formulaires

Quand un visiteur envoie le formulaire de contact ou demande un devis, la demande arrive dans la seconde sur Telegram, en plus de l'email.

Le visiteur remplit le formulaire et valide
Deux canaux en parallèle : FormSubmit (email, la trace) + POST /contatto (Telegram, l'alerte)
Tressy reçoit un message mis en forme, avec un bouton Répondre sur WhatsApp si le visiteur a laissé un numéro belge
  • Si un seul canal passe, le visiteur voit quand même sa confirmation
  • Si les deux échouent, repli automatique sur mailto: comme avant
  • Le message part vers tous les identifiants de ALLOWED_IDS : ajouter une personne au bot, c'est aussi lui donner les notifications
Anti-spam. Une URL publique qui pousse vers Telegram est une cible. Quatre protections se cumulent :
  • Champ piège (societe) invisible, placé hors écran et non display:none - que les robots ignorent moins souvent. Rempli => la demande est silencieusement jetée, le robot croit avoir réussi.
  • Contrôle d'origine : filtre à robots grossiers uniquement, trivial à falsifier (localhost est admis pour les tests).
  • Quotas : 5 envois par adresse IP et par heure, 40 au total. Compteurs en KV (c:<heure>:<ip>) avec expiration automatique après 1 h.
  • Échappement HTML de tout ce que le visiteur écrit, et longueurs plafonnées : le message est envoyé en parse_mode: HTML, du texte non échappé pourrait casser l'affichage.
Piège navigateur ancien. Les fetch sont construits à l'intérieur du try, et AbortSignal.timeout est appelé de façon optionnelle. Construits avant, un Safari antérieur à la version 16 levait une erreur de manière synchrone et cassait le formulaire sans même laisser le repli mailto:.

Passaporto : pourquoi on ne peut pas tricher

Un passeport auto-déclaratif se remplirait en trois clics depuis le canapé. Toute la validation se fait donc côté serveur.

Au camion le client demande le code du jour (4 chiffres, affiché dans le bot)
Worker vérifie : code juste ? région encore libre ? pas déjà tamponné aujourd'hui ?
5 régions → un code de retrait de 6 caractères s'affiche sur le téléphone du client
Tressy renvoie ce code au bot → ✅ valide, et le passeport est marqué utilisé
  • Code du jour : SHA-256(date + WEBHOOK_SECRET) - jamais stocké, impossible à deviner, change chaque nuit (la veille reste acceptée pour les fins de soirée)
  • Un tampon par jour maximum : le tour d'Italie demande donc 5 visites réelles
  • L'état vit dans KV, pas dans le téléphone : vider le navigateur ne redonne aucun tampon
  • Un seul dolce par passeport : la clé riscatto:<id> ferme la porte après retrait
  • Vie privée intacte : l'identifiant est un UUID anonyme. Aucun nom, aucun email, aucun cookie
Ce qui reste possible : un client présent au camion peut donner le code du jour à un ami absent. C'est l'équivalent exact d'une carte à tampons papier qu'on prête - et ça reste plafonné à un tampon par jour et par passeport. Pour verrouiller totalement, il faudrait que Tressy scanne elle-même chaque téléphone, ce qui ralentirait le service pour un gain marginal.

Mur Instagram

La page réseaux affiche les 6 dernières publications, servies par GET /instagram. Un cron tente un rafraîchissement chaque lundi 4h.

Limite connue : Instagram répond 429 aux serveurs Cloudflare, donc le rafraîchissement automatique échoue souvent. Dans ce cas rien ne casse : les publications précédentes restent affichées et le bot envoie un rappel Telegram. Mise à jour manuelle en 5 secondes : /instagram https://www.instagram.com/p/XXXX/
Solution définitive à mettre en place avec le client : Meta Graph API (gratuite et officielle). Nécessite le compte Instagram en Business/Creator lié à la Page Facebook, puis une app Meta. Le Worker existant l'appellera à la place du scraping.

Autoriser une nouvelle personne

# 1. Elle écrit au bot : il lui renvoie son identifiant Telegram
# 2. Ajouter cet identifiant à la liste (séparés par des virgules)
cd worker && npx wrangler secret put ALLOWED_IDS
Le token du bot peut être régénéré à tout moment via /revoke chez @BotFather - il faut alors le réenregistrer (npx wrangler secret put BOT_TOKEN) et refaire le setWebhook.

En place fait

  • Titre, méta-description, canonical et un seul h1 par page
  • Attributs alt sur toutes les images
  • JSON-LD FoodEstablishment (nom légal, TVA, adresse, téléphone, réseaux)
  • JSON-LD FAQPage sur /faq.html - éligible aux résultats enrichis Google
  • sitemap.xml (11 URLs) et robots.txt
  • Mentions légales en pied de page (obligation belge)

Google Search Console

  • Propriété tremorsi.com vérifiée par enregistrement TXT
  • Sitemap soumis - « Opération effectuée », 7 pages découvertes
  • Rapports complets disponibles après quelques jours de collecte

Auditer le référencement

Script audit_seo.py : il interroge les pages en ligne et contrôle l'unicité des titres, des descriptions et des h1, leurs longueurs, la hiérarchie des titres, les images et le maillage interne.

Leçon apprise. Une première version ne mesurait que la longueur des méta-descriptions, jamais leur contenu. Résultat : deux pages générées à partir de contact.html avaient hérité de sa description mot pour mot, et l'audit annonçait « tout est en ordre ». Un audit doit vérifier la qualité et l'unicité entre les pages, pas seulement la présence d'une balise.
  • Ajouter toute nouvelle page à la liste PAGES en tête du script, sinon elle n'est pas contrôlée
  • Le script interroge la production : ajouter ?cb=1 aux URLs pour contourner le cache CDN après un déploiement récent
  • Écrire les titres et descriptions en accents UTF-8 directs (é, à), pas en entités &eacute; : sinon le comptage des caractères est faussé et Google tronque
Piste d'évolution : créer une fiche Google Business Profile pour le food truck - c'est le levier n°1 pour les recherches locales « food truck italien Charleroi ».
